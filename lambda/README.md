# Angular SSR on AWS Lambda — what Cloud Run did not ask for

This folder is not an argument that Lambda is bad. It exists to make the
**adaptation cost concrete**, by showing the code that had to be written for
one platform and not the other.

## The scoreboard

| | Cloud Run | AWS Lambda |
| --- | --- | --- |
| SSR entry point | `src/server.ts`, **generated by `ng add`** | `lambda/server.lambda.ts`, hand written |
| Build configuration | the default one | an extra `lambda` configuration in `angular.json` |
| Protocol adaptation | none | `handler.mjs` — ~120 lines translating events ↔ HTTP |
| Infrastructure | one `gcloud run deploy` command | `template.yaml` (SAM) |
| HTML streaming | default behaviour | Function URL with `InvokeMode: RESPONSE_STREAM` only |
| Requests per instance | up to 80 concurrent | **one per execution environment** |
| Response ceiling | whatever HTTP allows | 6 MB buffered / 20 MB streamed |
| Static assets (JS, CSS) | served by the same container | in practice CloudFront + S3 in front |

The point in one sentence: **on Cloud Run, the artifact that runs on your
laptop is the artifact that runs in production.** On Lambda there is a
translation layer in between — and that layer is your code, which you own,
maintain and debug.

## The files

| File | Purpose |
| --- | --- |
| `server.lambda.ts` | Alternative entry point. Uses `AngularAppEngine` (web-standard API) instead of `AngularNodeAppEngine`. |
| `handler.mjs` | Converts the AWS event into a `Request` and the `Response` back into a Lambda result. Includes both buffered and streaming variants. |
| `Dockerfile` | Built on `public.ecr.aws/lambda/nodejs:22`, not on the official Node image. |
| `template.yaml` | SAM: function, Function URL, alias and provisioned concurrency. |

## Running it locally, without an AWS account

The Lambda build **overwrites** `dist/`, so rebuild the normal one afterwards.

```powershell
# 1. Build with the Lambda entry point
npm run build:lambda

# 2. Recreate the layout Lambda expects (handler.mjs next to dist/)
$staging = "$env:TEMP\lambda-test"
New-Item -ItemType Directory -Force $staging | Out-Null
Copy-Item .\dist "$staging\dist" -Recurse -Force
Copy-Item .\lambda\handler.mjs "$staging\handler.mjs" -Force

# 3. Invoke with a synthetic Function URL event
@'
import { handler } from './handler.mjs';

const event = {
  version: '2.0',
  rawPath: '/',
  rawQueryString: '',
  headers: { 'user-agent': 'local-test' },
  requestContext: {
    domainName: 'abc123.lambda-url.us-east-1.on.aws',
    http: { method: 'GET' },
  },
  isBase64Encoded: false,
};

const result = await handler(event);
const html = Buffer.from(result.body, 'base64').toString('utf8');

console.log('statusCode :', result.statusCode);
console.log('html bytes :', html.length);
console.log('has catalog:', html.includes('Mechanical Keyboard'));
'@ | Out-File "$staging\invoke.mjs" -Encoding utf8

$env:ALLOWED_HOSTS = "abc123.lambda-url.us-east-1.on.aws"
Push-Location $staging; node invoke.mjs; Pop-Location

# 4. IMPORTANT: restore the Cloud Run build
npm run build
```

Verified result: `statusCode 200`, ~17 kB of HTML with the catalog rendered.

## Two honest caveats

**1. Telemetry was not ported.** `src/server.ts` instruments every request
(instance identity, cold start, counters, structured logs) and injects that
data into the render through `REQUEST_CONTEXT`. `server.lambda.ts` does not —
so the telemetry bar falls back to its "no server data" state when the page is
served by Lambda.

That is not an oversight; it is the argument. **Each entry point carries its
own instrumentation.** Maintaining both means writing it, and keeping it
correct, twice.

**2. `allowedHosts` had to be repeated.** Each engine gets its own instance, so
Angular 22's SSRF protection had to be configured in both files. Forgetting it
in one makes every request return `400` — and only after deployment, once the
real domain shows up.

## When Lambda is the right call

Lambda wins when:

- the organization already runs on AWS, with IAM, VPC and observability in place;
- traffic is very bursty and per-invocation billing granularity pays off;
- the app already sits behind CloudFront, which handles static assets and caching.

The narrow claim here is only this: **for hosting Angular SSR specifically**,
Cloud Run requires less glue, because Angular's build output already is what it
expects — an HTTP process in a container.
